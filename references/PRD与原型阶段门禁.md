# PRD 与原型阶段门禁

## 1. 范围确认

正式产出前确认：

- 要解决的问题和业务目标。
- 目标用户、角色和使用场景。
- 功能范围、非目标和系统边界。
- 核心流程、关键规则、权限或数据范围。
- 交付用途、目标版本和已有上游材料。

信息不足且会改变方案时先提问。可以局部推进的未知内容标记为“待确认”，不得自行补造业务事实。

## 2. PRD Draft

PRD 应记录：

- 文档版本、阶段、状态和修订记录。
- 上游依据、下游原型和待确认项。
- 背景与问题、目标与非目标、用户与场景。
- 业务流程、功能需求、业务规则、权限或数据范围。
- 默认、状态、异常和验收标准。
- 风险、依赖和已确认决策。

使用稳定编号建立追踪关系。可按实际需要使用：

- `G`：目标。
- `S`：场景。
- `SR`：场景需求。
- `FR`：功能需求。
- `BR`：业务规则。
- `EX`：异常或边界。
- `AC`：验收标准。
- `R`：风险。
- `Q`：待确认项。

不要为了填满模板编造内容。PRD 聚焦产品与业务，不主动扩写数据库表、接口实现或研发技术方案。

用户明确确认 PRD 后，记录 Requirements Baseline，才能进入 HTML 原型。

## 3. HTML 原型 Draft

HTML 是首个可评审原型，也是 Figma 写入前的结构与视觉事实源。

要求：

- 首屏直接呈现可操作产品界面，不制作营销页或纯说明拼图。
- 页面、弹窗、表单、列表、筛选和反馈具备可评审交互。
- 覆盖 PRD 核心流程，并按业务需要表达默认、加载、空、禁用、成功、失败和无权限状态。
- 页面、功能、状态和关键交互可回溯到 PRD 需求编号。
- 不在 HTML 中擅自新增未确认的业务能力。
- 检查目标桌面视口；需求涉及响应式时，再检查移动视口。

用户明确确认 HTML 后，记录 UI Design Baseline，才能写入 Figma。

## 4. Figma 原型

输入必须是已确认的 PRD 和 HTML。

- 写入前确认目标 Figma 文件、目标页面、写入范围和预期根 Frame。
- 使用 Figma 官方 MCP 创建原生可编辑节点。
- 优先复用目标文件中的组件、变量、样式和图标。
- 不使用整页截图冒充可编辑原型。
- 不在 Figma 阶段修改已确认业务流程或新增能力。
- 写入后回读截图和节点结构，核对名称、尺寸、层级、文案、状态与交互表达。

## 5. 变更回退

| 变更类型 | 回退动作 |
|---|---|
| 范围、角色、业务流程、规则、权限变化 | 更新 PRD，重新确认，再同步 HTML |
| 页面布局、视觉、提示文案、交互表达变化 | 更新 HTML，重新确认 |
| Figma 与已确认 HTML 不一致 | 定点修正 Figma，重新截图和结构回读 |

## 6. 默认停止边界

流程默认在 Figma 原型交付后结束。除非用户重新明确扩大范围，否则不生成技术 Design、研发 Tasks、生产代码、测试用例、测试报告或发布材料。
